■ 2. 今あるもの（9/4〜9/8 に済んでいる）

  - Cloud Run サービス homis-karte-writer（東京・4Gi/2CPU・timeout 300・concurrency 1・蓋 max-instances 3・min 0）
  - 合言葉（X-Writer-Key）・HOMIS の ID/PW は Secret Manager。HOMIS は専用の「おひさまロボット GCP」アカウント
  - 失敗の扱い（仕様 7章）: 新規ボタンのあとは中でやり直さない／orderId で二重を断る（試験で 2回目 409）
    空カルテ疑いは DX に Chat（Webhook は Secret・未作成）
  - 試験: 1件 約45秒／別の患者3人同時は3枚／同じ患者の同時は1枚に重なる（HOMIS の性質）
  - 結果シート「HOMIS書込結果」は試験用の別ブック。ナビ（GAS）は未接続


■ 3. 決めたこと（v0.2・黒ヤギの意見つき）と、岩城さんに決めていただくこと

  決め1  ナビから Cloud Run をどう呼ぶか → 案B（Cloud Tasks の列を挟む）に一本化（黒ヤギも強く推し）

    案B: ナビは「順番待ちの列」（Cloud Tasks・東京）に入れるだけ。列が Cloud Run を1件ずつ呼ぶ（同時 1・再試行 0）
      - 今の垂水と同じ「1件ずつ」なので、同じ患者の重なり・蓋の 429・ナビの待ち時間の問題が出ない
      - 列が Cloud Run の認証を代わりにする（IAM。合言葉も残す）
    案A（ナビから直呼び）は採らない: 集団40名を1回の撮影完了で順に呼ぶと 40×約45秒 ＝ 約30分で、
      GAS の1回の実行の上限 6分（公式 quotas: Script runtime 6 min / execution）を必ずこえる。
      UrlFetch の1回の待ちの上限は公式の制限ページに記載なし【推測: 約60秒と言われる】

    【岩城さんに確認】列の中の一時保存（東京・届けたら消える）が「保存はしない」（9/4 決定）の範囲に入るか

  決め2  「書けた」の知らせ方 → Cloud Run が書き終えたら、ナビの doPost を呼ぶ（今の垂水と同じ流れ）（黒ヤギ指摘1）
      - ナビの updateHomisLink_ ／ sendGroupCompleteNotification_ をそのまま使える。ナビに時間トリガーを入れない
      - v0.1 の「ナビが結果シートを1分おきに見る」はやめた
        （黒ヤギの「1日90分の上限で止まる」は一般アカウントの値。nhw.jp は Workspace で 6時間/日（公式 quotas）。
         上限の心配ではなく、仕組みを今と同じにできるので採った）
      - 知らせの失敗（穴3）の手当て: Cloud Run は応答が無い／5xx のときだけ 3回まで間をあけて再送。
        だめなら DX の Chat に「撮影完了 Chat が出ていない注文」を知らせる
      - 二重 Chat の手当て（必須）: 今の updateHomisLink_ は2回呼ばれると撮影完了 Chat も2回出る（Order.gs 2162〜2248行。
        「送った」の印が無い）。ナビ側で「この注文は通知済み」を **CacheService（自動で消える一時メモ・6時間）** に覚え、
        2回目は Chat を出さない。再送は数分のうちに起きるので6時間で足りる。スクリプトプロパティには溜めない
        （1つの入れ物の合計 500KB の上限・公式 quotas「Properties total storage」に、印が月100〜150件ずつ溜まって当たるため。黒ヤギ2回目 指摘2）
        GRP_BATCH_（集団の覚え）は今どおりスクリプトプロパティ。送ったら消える（今の作り）
        CacheService は期限前に消えることがある（公式: not guaranteed to retain data until expiration）。そのときは Chat が
        まれに二重になる。これは許容する（黒ヤギ3回目 指摘3）。カルテの二重は Cloud Run の orderId（409）で必ず止まる

  決め3  集団のまとめ通知
      - 主: ナビの updateHomisLink_ が、その回の一括完了で覚えた注文（GRP_BATCH_）が全員そろったら sendGroupCompleteNotification_ を出す
        （失敗した人も Cloud Run は空の URL で知らせるので、数はそろう＝今の垂水と同じ）
      - 予備: 全員そろわないまま時間がたったら DX の Chat に知らせる（人が判断。自動では全員に送らない）
        動かす主体（黒ヤギ2回目 指摘1。ナビには時間トリガーが無いので、外から起こす）:
          ナビが集団の注文を列に入れるとき、最後に「確かめ役」の予約を1つ入れる（Cloud Tasks の scheduleTime ＝
          入れた時刻＋人数×1分＋10分）。その時刻に Cloud Run がナビの doPost（新しい action「checkGroupComplete」）を呼び、
          ナビが「その回の全員がそろったか」を見る。そろっていなければ DX Chat。そろっていれば何もしない
          → Cloud Run が途中で落ちても、予約は列に残っているので確かめは必ず動く
          画面で見つける案（スタッフが開いたときに警告）は、画面を変えるので採らない
          誤った警告を出さない（黒ヤギ3回目 指摘1）: そろっていなくても、直近10分以内にその回の知らせが1件でも来ていれば
          「まだ書いている途中」とみなして警告しない。その場合は確かめ役をもう一度10分後に予約し直す（最大3回まで）
        doPost の今の action（updateHomisLink・sendGroupCompleteNotification）の名前と動きは変えない。足すだけ
      - 今の sendGroupCompleteNotification_ は「覚えが無いと全員に送る」。GCP のときは覚えが無ければ送らないように分ける（二重送信を防ぐ）

  決め4  切り替えの単位 → 個別も集団も一度に（スクリプトプロパティ HOMIS_WRITE_MODE=3。戻すときは 1。デプロイ不要）（黒ヤギも同意）

■ 5. 切り替えの手順（フェーズ3・平日の朝 9時台）

  1. 撮影完了が入っていない時間を選ぶ
  2. 垂水の監視フォルダ（Homis登録データ）の未処理 JSON が 0件であることを確かめる（黒ヤギ指摘5）
  3. スクリプトプロパティ HOMIS_WRITE_MODE=3
  4. 最初の1件で、列 → Cloud Run → HOMIS → 撮影完了 Chat（1回）まで確かめる
  5. 切り替えのあとに垂水のフォルダへ新しい JSON が来ないこと（MODE=3 ではドライブに置かない）を確かめる
  戻すとき（黒ヤギ2回目 指摘3）:
    1. Cloud Tasks のキューを止める（pause）。新しい注文は列から出ていかなくなる
    2. いま Cloud Run で書いている1件の終わりを待つ（最大5分。Cloud Logging の RESULT で確かめる）
    3. 列に残っている注文番号を控える。列に入れるときの名前（タスク名）に注文番号を入れておくので、一覧の名前の列だけを写す。
       本文（患者情報）は開かない（黒ヤギ3回目 指摘2）。確かめ役はタスク名に groupId を入れる
    4. 列を空にする（purge）。あとで再開しても古い注文が流れないようにする
    5. HOMIS_WRITE_MODE=1（このあとの撮影完了は垂水へ）
    6. 3 で控えた注文だけ、ナビの管理者用の一度きりの関数でカルテ用 JSON を垂水のフォルダに置き直す（フェーズ2 で用意しておく）
    7. 確かめ役の予約（決め3）も 4 で消える。その回の集団のまとめ通知は 6 のあと垂水の流れで出る

■ 9b. フェーズ2 で分かったこと（10/15）

  - Cloud Tasks は、終わった（消えた）タスクの名前を数時間〜数日は使い直せない（公式 Task.name）。タスク名＝注文番号なので、
    同じ注文の入れ直しは 409（入った扱い）になり書かれない。Cloud Run も同じ注文は結果シートで断る（仕様 7.2 #9）。
    やり直しが要るときは人が判断する（HOMIS で直す・別の注文番号で出し直す）
  - GAS の ScriptLock は1つなので、鍵の中でメールを送ると、送信記録（Notification.gs appendMailLog_）が鍵を取って外し、外側の鍵も外れる。
    フェーズ2 のまとめ通知は鍵の外で送る形にした（黒ヤギ 10/15）。
    【あとで】今の版でも quickConfirmSchedule・registerGroupExam・addPatientToGroup・confirmGroupSchedule が鍵の中で通知を送っている
    （v8.8.0〜v8.9.0）。鍵が途中で外れるだけで、今のところ二重などは見えていない。線E か次の応急処置で直す（今回は直さない）
