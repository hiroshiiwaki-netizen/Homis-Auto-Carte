------------------------------------------------------------
■ 1. 目的

  ・カルテライターが書いた結果（成功・失敗）を、白ヤギに聞かなくても画面で見られるようにする
  ・失敗したものを、画面の「再書き込み」で書き直せるようにする
  ・FAX（OhiScanGo）・問い合わせ・疑義照会をタブで分け、全記録は日付・エラーでしぼり込む

■ 2. 岩城さんが決めたこと（11/6）

  1. 送られてきた中身は JSON で残す。置き場は Cloud Storage（案1）
  2. 残す期間は 60 日（様子を見て変える）
  3. 見られるのは全職員（app.nhw.jp の今の決まりどおり）。管理の操作（記録の削除など）は DX推進部だけ
  4. ライターが動いているかの印を出す
  5. 試験の行はふだん隠し、切り替えで出す
  6. 送った人を出す
  7. FAX は患者さんの名前と書類種を出す。ほかの道も、見て誰の何か分かるようにする
  8. 見た目は画面案の方向（行の背景をうっすら色分け・左の色帯はやめる）
  9. 実行リストの第1段を、共通 JSON の入口より先に作る
 10. DX推進部の見分けは、箱に DX推進部のメールの一覧を持たせる（環境変数 DX_ADMINS）

■ 3. やらないこと

  ・今の FAX・問い合わせ・疑義照会の道（Tukusi → 受け口 → 列 → ライター）の動きは変えない
    （受け口の timeout 30 秒・列の同時 1 件・maxAttempts 1 はそのまま）
  ・ライターの書き方（画面を操作するロボット）は変えない。HOMIS に直接書く JS は使わない（11/5 決定）
  ・結果シート（RESULT_SPREADSHEET_ID）はやめない。二重書き防止の札として今までどおり使う
  ・患者さんの名前・本文を Cloud Logging（ログ）に出さない。名前は JSON の中だけ
  ・保存されたかもしれない失敗に、ワンクリックの再書き込みは出さない（カルテが 2 枚になるため）

■ 4. 全体の流れ

  Tukusi ─→ 受け口 ─→ 列 ─→ ライター ─→ HOMIS
                                │
                                ├─→ 結果シート（今まで通り）
                                └─→ 記録の JSON（新）  gs://<記録の置き場>/records/<日付>/<注文番号>.json
                                                    ↑ 読む・対応を書き足す
  職員のパソコン ─→ app.nhw.jp/kartelog/（IAP・全職員）─→ 実行リストの箱（Go）
                                                    └─→ 再書き込み: 受け口の新しい入口 /retry → 同じ列

■ 5. 記録の JSON（1 注文 = 1 ファイル）

  置き場: 新しいバケット（東京・60 日で自動削除・一般公開なし）。名前は【確認】実装時に決める
  パス:   records/YYYY-MM-DD/<注文番号>.json（日付は受付の日・日本時間）
          再書き込み（-R1・-R2）は、押した日ではなく元の注文の日のフォルダに置く（黒ヤギ 2回目 指摘2）

  中身:
    order_id        注文番号（FAX-… / BOT-… / BOT-G-… / -R1 付きは再書き込み）
    route           fax / bot / bot_g / retry（どの道か）
    received_at     受付時刻
    status          received（受け口で受けた）/ rejected（受け口で落とした）/ accepted / running / ok / fail / done（対応済み）
    error_type      FIELD_REASON のキー（例 verify:o_mismatch）。受け口で落としたときは skip:… / error:…
    left_in_homis   HOMIS に残したもの（ライターが書く。再書き込みの判定はこれで行う）
                      none     ＝新規を開く前に止まった（カルテは無い）
                      editing  ＝ライターの書きかけ（編集中）が残っている
                      saved    ＝保存した／保存したかもしれない
                      unknown  ＝分からない（台が途中で落ちた・古い JSON）
                    決め方（黒ヤギ 2回目 指摘1）: 新規を開いていない → none／
                      保存（完了・中断）を押したあと → saved（no_karte_id・verify:* を含む）／
                      stopped・left_editing＋blocked・reused_editing → editing／
                      新規は開いたが、保存を押したかがコードから分からない（opened_then_fail・step:…）→ unknown
                      （実装 v3.11.0 で安全側に寄せた。押したあとに落ちた筋を editing と言うと二重カルテになるため）
    homis_url       書いたカルテの URL
    patient         { homis_id, name }   name はライターが HOMIS の患者ページから読む【確認】読む場所
    doc_type        書類種（FAX は受け口の doc_type。問い合わせ・疑義照会は「問い合わせ」「疑義照会」）
    source／fax_route  FAX の差出元（Tukusi の source）と経路（垂水FAX など）
    sender          送った人（FAX は差出元 source／問い合わせ・疑義照会は sender_email【確認】Tukusi に足す）
    payload         送られてきた中身（S・O の本文など。再書き込みに使う）
    timeline        [{at, what}] 受付・書き始め・書き終わり・読み直し の時刻
    actions         [{at, who, what}] 再書き込み・手で書いた・削除 を押した人と時刻
    retry_of / retried_as  再書き込みの元と先の注文番号

  書く人:
    ・受け口: 受けたとき（received）と、落としたとき（rejected・理由つき）に書く。
              列に入れたあとは触らない（黒ヤギ 1回目 指摘1: 受け口で落ちたものが一覧から消えないように）
    ・ライター: 受け取ったとき（accepted）と、終わったとき（ok / fail・left_in_homis）に上書き
    ・実行リストの箱: 対応（手で書いた・再書き込み）を actions に足し、status を done にする
  書けなかったとき: カルテの書き込み・受け口の返事は止めない。Cloud Storage への書き込みは 1 回 5 秒まで、
                    失敗はログに 1 行だけ（今の結果シートの失敗と同じ扱い）
  古い JSON: 項目が足りなくても読めるようにする（Go の構造体は全部省略可。無い left_in_homis は unknown）

■ 6. 画面

  タブ: 全記録・OhiScanGo（FAX-）・問い合わせ（BOT-）・疑義照会（BOT-G-）・音声カルテ（準備中）
  上の印: 今日の件数と成功率・時間ごとの棒・書けた／書けなかった／途中
          ライターの最後の書き込み時刻と、列で待っている件数（止まっていたら赤）
  知らせ: 書けなかったものがあるときだけ赤い枠と「書けなかったものだけ見る」
  止まっているかも（黒ヤギ 2回目 指摘3）: received・accepted・running のまま 15 分を過ぎ、しかも列にその注文が無い
          （列で待っているだけではない）ものは「⚠ 止まっているかも」と出す。再書き込みは出さない（unknown 扱い）。
          列で待っているものは「列で待っています（前に○件）」。11/5 夜は 31 件の束で最後が約 25 分待ったため、時間だけでは決めない
  しぼり込み: 今日・昨日・7 日・日付／成否／エラーの種類／注文番号・患者さんの名前で検索
              試験の行（FAX-MIRROR-…）は「試験も出す」を押したときだけ
  一覧の 1 行: 時刻・状態・道・患者さんの名前・書類種・送った人・理由・右のボタン
              行の背景: 書けた＝薄い緑／書けなかった＝薄い赤／途中＝薄い黄／対応済み＝薄いグレー
  右のボタン: 書けた → カルテを開く
              書けなかった（保存されていない失敗）→ ↻ 再書き込み
              書けなかった（保存されたかもしれない失敗）→ 🔍 先に確かめる
  詳しい窓: 注文番号・時刻の流れ・理由・次にすること・送られた中身（S・O）
            ボタン: 再書き込み／✍️ 手で書いた（対応済みにする）
  更新: 1 分ごとに自動で読み直す＋「読み直す」ボタン
  PWA: ホーム画面（パソコンのアプリ一覧）に入れられる。画面の部品だけ手元に持ち、データは毎回読む

■ 7. 再書き込み

  判定はエラーの種類ではなく、ライターが書いた left_in_homis で行う（黒ヤギ 1回目 指摘2）。
  同じ blocked:in_progress_karte でも、1回目の書きかけを残したあと（server.py 784 行）なら editing になるため。

  none（カルテは無い）→ ↻ 再書き込み をそのまま押せる
    例: locked:busy・locked:error・login・新規の前の blocked（1回目の書きかけが無いとき）・受け口で落とした rejected
  例外: error_type が skipped:new_karte_found（14.2b・人が書いた見込み）は left_in_homis が none でも、どんなボタンも出さない
        （黒ヤギ 自動やり直し仕様2回目 指摘3）
  editing（ライターの書きかけが残っている）→ 再書き込みは出さない
    案内:「HOMIS でこの患者さんの編集中のカルテを取り消してから」。
         「編集中のカルテを取り消した」に印を付けたときだけ ↻ 再書き込み を出す
    例: stopped:unverified_input・left_editing のあとの blocked・blocked:reused_editing
  saved（保存した・したかもしれない）→ 再書き込みは出さない（印を付けても出さない）
    案内:「カルテを開いて確かめ、足りなければ手で足す」→ ✍️ 手で書いた で閉じる
    例: no_karte_id（保存のあと番号が取れない＝11/2 の例）・verify:*
  unknown → saved と同じ扱い（安全側）

  流れ:
    1. 箱が JSON の payload を読み、受け口の新しい入口 /retry に送る（押した人を添える）
    2. 受け口は注文番号に -R1（2 回目は -R2）を付けて、元と同じ列に入れる
       → 同じ列・患者さんごとの札・二重書き防止がそのまま効く
    3. 元の JSON は status=done・retried_as=-R1。新しい JSON は retry_of=元
  上限: 1 件につき 2 回（-R2 まで）。それ以上は手で書く
  ボタンが出るのは、つながり（元 → -R1 → -R2）の一番新しいものが fail で確定したときだけ。
    -R1 が received・accepted・running の間は、元にも -R1 にもボタンを出さない（黒ヤギ 1回目 指摘3）
  二度押し: 箱は元の JSON を世代番号つきで書き換えて（ifGenerationMatch）「再書き込み中」の印を取る。
    取れなかった方は止める。受け口の列の名前（-R1）でも 409 で止まる。
    印を取ったあと受け口へ送れなかったら、印を外して「もう一度押してください」

■ 8. 誰が何をできるか

  全職員:    見る・カルテを開く・再書き込み・手で書いた
  DX推進部:  上に加えて、記録の削除・試験の行の表示・押した記録の取り消し
  見分け方:  IAP の署名つきヘッダー（X-Goog-IAP-JWT-Assertion）を箱で検証し、そのメールを DX_ADMINS と比べる。
             署名の無い・合わない呼び出しは全部断る
  入口:      箱の Cloud Run は ingress=internal-and-cloud-load-balancing・認証なしの直接呼び出しは不可（run.app から入れない）
  再書き込み: 箱 → 受け口 /retry は、受け口の鍵（Secret）＋押した人のメールを添える。受け口は /retry を箱からだけ受ける

■ 11. テストの方針

  ・JSON: 受付→成功／受付→失敗／受け口で落とした／書いている途中で台が止まった（accepted のまま）を、偽の Cloud Storage で
  ・受け口: Cloud Storage が 10 秒返事をしなくても、5 秒であきらめて列に入れ、Tukusi に 200 を返す
  ・日付またぎ: 前の日の失敗を次の日に再書き込みしても、元の日のフォルダに置かれ、つながりが見える
  ・left_in_homis: server.py の失敗の分かれ道すべて（blocked・locked・stopped・left_editing＋blocked・no_karte_id・verify）で
    正しい値になるか。Cloud Storage が遅い・権限なしでも書き込みと受け口の返事が止まらない
  ・画面: 架空の JSON を置いて、タブ・しぼり込み・件数が合うか。名前の検索
  ・再書き込み: 押せる／押せないを left_in_homis の 4 つで。二人同時・-R1 が途中の間・印を取ったあと送れない・-R3 で止まる・列の 409
  ・結合: テスト舞子で 失敗→再書き込み→カルテが 1 枚だけ を本物で
  ・権限: DX推進部以外で削除が押せない（画面と箱の両方で止まる）。署名なし・偽の署名・run.app からの直接呼び出しを断る

  13.1 引く先
    おひさまシステムの Data API（つなぎ先は ID統合計画の同期と同じ FM_HOST・データベース）
    レイアウト API_M_PATIENT_LINKINFO を _find で homisID 完全一致（"==<番号>"）
    使う項目: 氏名（patient_name・無ければ SEI＋MEI）・ORCAID・クリニック名
      ※項目の名前は作る前に今の FM の GET /layouts/API_M_PATIENT_LINKINFO（項目名だけ）で確かめる（DDR は古い）
    ログイン: 既存の Secret fm-sun-patient-user・fm-sun-patient-password（実行リストのアカウント kartelog-app に読む許可だけ足す）
    読むだけ。FM に書かない・スクリプトを動かさない

  13.2 引き方（黒ヤギ 仕様1回目 指摘1・3・6 を反映）
    ・一覧の返事は FM を待たない。覚えている分だけ名前を付けてすぐ返し、まだ覚えていない番号は
      箱の裏の係（1 つだけ）に頼む。係が 1 件ずつ（同時に 2 件まで）引いて覚え、次の読み直し（1 分）で名前が出る
    ・同じ番号の頼みは 1 回にまとめる（何人が同時に開いても、1 つの番号を FM に引くのは 1 回）
    ・頼みの列は 100 件まで。あふれたら古い頼みを捨てて新しい頼み（今書かれたカルテ）を先にする。FM を休んでいる 60 秒は頼みを受けない
      （黒ヤギ 仕様2回目 指摘1）。捨てた番号は次の読み直しでまた頼まれる
    ・覚えの表と頼みの印は鍵（sync.RWMutex）で守る。テストは go test -race（黒ヤギ 仕様2回目 指摘4）
    ・引いた結果は箱の中に 24 時間覚える（見つからなかった＝空も覚える。ただし 1 時間で忘れて引き直す）
    ・箱は最大 2 台。覚えは台ごとなので、別の台に当たると一度だけ番号に戻ることがある。その台もすぐ引いて次の読み直しで名前が出る
      （名前を置き場に書かない決まりを優先し、台どうしで共有しない）
    ・FM のセッションは 1 つを使い回す。切れたら（401・952）鍵をかけて 1 つの係だけが取り直し、ほかはそれを待って使う。箱を止めるときに閉じる
    ・FM が止まっている・遅い（1 件 5 秒）ときは、その回は患者番号のまま出す。続けて失敗したら 60 秒は引かない（記録と同じ考え）
    ・homisID が 1 件に決まらない（0 件・2 件以上）ときは名前を出さない。一覧はふつうの「患者番号 ○○」（引けないときと同じ）。
      詳しい窓だけに「おひさまシステムで見つからない番号です（2 つ目のクリニックの番号など）」と小さく書く（黒ヤギ 仕様2回目 指摘3: 毎日出る警告は形だけになる）
      ※取り違えを出さない（10/13 の調べでは重複 0 件だが、決め打ちしない）
    ・番号の形（1〜10 桁の数字）でないものは引かない。引く前に前後の空白を取る。完全一致（"==<番号>"）で引く
    ・できないこと（黒ヤギ 仕様1回目 指摘2）: 2 つ目以降のクリニックの HOMIS 番号（FM の N_HomisID・約 270 行）は
      API の口に無いので引けない。その番号で書いたカルテは上の「確認できません」になる。Solcore に替えたときに直す
    ・クリニック名は「その HOMIS 番号のクリニック」（HOMIS の番号はクリニックごとに別のため。主の番号で見つかったときだけ出る）

■ 14. 書込失敗の自動やり直し（ライター 3.12.0・実行リスト 0.3.0）

  岩城さん 11/6:「失敗したカルテのリトライ、自動でできないか。何回かリトライして、駄目なら人間が確認」
    回数と間: 3 回（5 分後・15 分後・30 分後）／知らせ: 今までどおりすぐ出し「自動でやり直します」を添え、最後にだめなら「手で書いてください」
    進め方: 仕様 → 黒ヤギ → 作る → テスト → 黒ヤギ → 配置（いずれも「おすすめで OK」）
  画面の「再書き込み」ボタン（7章・第3段）は、この自動やり直しのあとに残った失敗を人が扱うためのもの（今回は作らない）

  14.1 やり直してよい失敗（全部満たすときだけ）
    ・left_in_homis = none（HOMIS に何も残っていない・7章）
    ・error_type が次のどれか: locked:busy・locked:error・blocked:in_progress_karte・blocked:unexpected_alert・login・chrome・timeout
      （blocked:in_progress_karte はライターが中で 90 秒あけて 1 回やり直したあとの失敗）
    ・型紙が fax_so か bot_s_interrupt（レントゲンはやらない）
    ・注文番号が本番（FAX-・BOT-・BOT-G-）か試験の BOT-TEST-（試し書き FAX-MIRROR- はやらない）
    ・まだ 3 回やっていない（回数は注文番号の末尾 -A1〜-A3 を決まった形 ^(.*)-A([1-3])$ でだけ読む。読めなければ 0 回。
      -A3 の失敗のあとは、どんな場合も列に入れない＝上限をコードで固定・黒ヤギ 仕様1回目 指摘3）
    ・人が書いた見込みが無い（下の 14.2b）
    saved・editing・unknown、verify:*・no_karte_id・stopped:*・blocked:reused_editing・受け口で落とした rejected はやらない（人が確かめる）

  14.2 やり直しの入れ方
    ・注文番号は元の番号＋「-A1」「-A2」「-A3」（A＝自動）。2 回目以降は元の番号に付け直す（-A1-A2 にしない）
    ・ライターが失敗を確定したあと、同じ列（FAX は homis-fax-writer・問い合わせ／疑義照会は homis-bot-writer）に
      予約の時刻（scheduleTime）つきで入れる: 1 回目の失敗 → 5 分後に -A1、-A1 の失敗 → 15 分後に -A2、-A2 の失敗 → 30 分後に -A3
    ・中身は今回の注文と同じ（S・O・患者番号・型紙）。recordDay も同じ（元の注文の日のフォルダ）
    ・列の名前＝注文番号なので、同じやり直しを 2 回入れても 409 で 1 回になる。結果シートも注文番号で二重を断る
    ・入れられなかったとき（権限・列の不具合）は、やり直しをあきらめて「手で書いてください」を出す（14.4）
    ・ライターが列に入れるための設定: RETRY_MODE（off／on・既定 off）・WRITER_URL・TASKS_INVOKER_SA・FAX と問い合わせの列の名前。
      ライターのアカウントに列への投入（cloudtasks.enqueuer）と、呼び出しのアカウントを使う許可が要る（岩城さんの操作）

  14.2b 人が書いた見込みの守り（黒ヤギ 仕様1回目 指摘2）
    ・最初の失敗を確定したとき、その患者さんのカルテ一覧（読むだけ・getKarteList）の一番新しいカルテ番号を記録に控える（baseline_karte_id）
    ・やり直し（-A1〜-A3）は書き始める前に同じ一覧を読み、控えより新しいカルテがあれば「人が書いた見込み」として書かずに止める。
      記録は fail・error_type=skipped:new_karte_found・left_in_homis=none、DX に知らせる。現場には出さない（人がもう書いているため）
    ・ほかの方が別のカルテ（訪問の記録など）を書いた場合も止まるが、二重カルテより安全側
    ・一覧が読めないときは、書かずに止めて同じ扱い（分からないときは書かない）
    ・作るときの決まり（黒ヤギ 仕様3回目【進めてよい】の3点）: DX への知らせに見つけた新しいカルテの番号・日付・患者ページの直リンク／
      カルテ番号は数（int）で比べる／控えは失敗が分かった直後（札を外す前）に取る
    ・残る危険（黒ヤギ 仕様2回目 指摘2）: blocked:in_progress_karte の原因の「入力途中のカルテ」（訪問の予定など）を現場が完了しても、
      カルテ番号は増えないので止まらない。これは自動やり直しの目的そのもの（予定が片付いて新規が開けるようになったら書く）で、
      一覧には状態の項目が無く「FAX の中身を書いて完了した」か「予定として完了した」かを見分けられない。
      最初の知らせの【手で書かずにお待ちください】で防ぐ

  14.3 記録（実行リスト）
    ・元の注文（またはひとつ前のやり直し）の JSON: status を handed_over（自動で再書込へ）・retried_as に次の番号・retry_at に予約の時刻
    ・次の番号の JSON を「無いときだけ作る」で先に作る: status scheduled・retry_of・retry_at・attempt（1〜3）・payload
    ・画面（岩城さん 11/6「一覧で何分以内に再試行と記載」「本当にだめな分は手動でお願いします、とわかれば」）:
      handed_over は薄いグレー「↻ 自動で再書込へ」、scheduled は薄い黄「⏳ 自動で再書込（10:35 まで・あと 2 回）」、
      3 回ともだめ（-A3 の失敗）・やり直しを入れられなかった ものは赤「✋ 手動でお願いします」。
      人が書いた見込みで止めた（skipped:new_karte_found）ものは「手動でお願いします」と出さない。グレー「☑ 人が書いた見込み（自動の再書込を止めました）」
      （黒ヤギ 仕様2回目 指摘1: 書いた人がもう一度書かないように）
      やり直しの結果は今までどおり（書込成功）。数字のカードは「最後の結果」だけで数える（handed_over は数えない）
    ・止まっているかもの判定（6章）: scheduled は予約の時刻から数える

  14.4 現場への知らせ（今までの知らせはそのまま・文を足す）
    ・元の注文が失敗し、やり直しを入れたとき: 文の先頭に【手で書かずにお待ちください】、続けて今までの文と
      「カルテ書込を自動でやり直します（最大 3 回・約 50 分以内）。結果は実行リストで見られます。最後まで書けなかったときだけ、
      改めて『手で書いてください』とお知らせします。」（黒ヤギ 仕様1回目 指摘2・2回目の文の提案）
    ・-A1・-A2 が失敗したとき: 現場には出さない（DX にだけ「自動やり直し 1 回目も失敗・次は 15 分後」）
    ・-A3 が失敗したとき、またはやり直しを入れられなかったとき: 現場に「自動で 3 回やり直しましたが書けませんでした。手で書いてください」＋理由・患者ページ・注文番号
    ・やり直しで書けたとき: 現場には出さない（岩城さん 11/6「これは知らせなくていい」。黒ヤギ指摘1 を受けて確かめ直しても同じ。
      代わりに最初の知らせで「だめなときだけ改めて知らせる」「手で書かずに待つ」「実行リストで見られる」と伝える）。DX にだけ一言

  14.4b 書込後確認の記録（岩城さん 11/6「カルテ書込 ○・書込後確認 ○」）
    ・ライターが読み直し（verify_karte）の結果を記録の JSON に verify（ok／o_mismatch など／unverified）として残し、
      時刻の流れに「書込後確認 ○／×／未確認」を足す。画面: ok＝「書込後確認 ○」、不一致＝「書込後確認 ×」、
      unverified＝「書込後確認 未確認（カルテは保存済み）」（× と分ける・黒ヤギ 仕様1回目 指摘4）

  14.5 やらないこと
    ・保存したかもしれない・書きかけが残る失敗のやり直し（二重カルテになる）
    ・夜間・休日を避ける工夫（予約は時刻どおり。入力途中のカルテが夜まで残れば 3 回とも失敗し、手でとなる）
    ・回数・間を画面で変えること

  14.6 テスト
    ・やり直してよい失敗の判定（14.1）を全部の失敗の種類で
    ・番号の付け方（元→A1→A2→A3・付け直し）・予約の時刻・列の名前の 409・入れられないとき
    ・記録: 元が handed_over・次が scheduled・成功で最後の結果だけ数える・止まっているかもの時刻
    ・知らせ: 1 回目に文が足される・A1/A2 は現場に出ない・A3 で手で書いてください・成功は現場に出ない
    ・上限: -A3 の失敗で列に入らない／末尾が -A1-A1 などおかしな番号でも 3 回を超えない
    ・人が書いた見込み: 控えより新しいカルテがあれば書かない／一覧が読めなければ書かない
    ・結合: 偽の列で 失敗→A1 予約→A1 成功、失敗×4→最後に手で、を本物のライターの流れで
    ・本物: テスト舞子の BOT-TEST で locked:busy を作って 5 分後に A1 が書けること（配置後）
